# 0.26.1 · 예측 파일의 점수 분포 압축 (실행 전 설계)

## 요청과 범위
- 목적: `data/football/predictions.js`(6.79MB, 전송 약 1.5MB)를 줄여 첫 화면 전송량을 낮춘다. 리그 2개 추가(0.27.0) 전에 예측 파일 형식을 정리한다.
- 범위: 예측 파일 안의 경기별 점수 분포(`scoreDistribution`)를 담는 형식. 승·무·패 확률, 점수 요약(`score_summary`), 화면, 모델은 바꾸지 않는다. F1은 범위 밖.
- 담당(MatchDesk 5인): 팀장 계획·결재 → 시각화·웹(구현) → 독립 검증. 확률 값 자체를 다시 계산하지 않으므로 수집·분석·예측 담당은 생략하고 그 사실을 기록한다. 구현자와 검증자는 서로 다른 하위 에이전트. main 병합은 사용자 결재.

## 현재 구조 (2026-10-20 측정)
- 경기 641개마다 0~12골 × 0~12골 = 169칸의 점수 확률이 `{"home":h,"away":a,"probability":p}` 객체로 들어 있다. 파일의 약 90%가 이 부분이다. 모든 경기가 169칸이고, 순서는 홈 득점 0→12, 그 안에서 원정 득점 0→12로 같다.
- 이 값을 쓰는 곳은 8비트 경기 시뮬레이션 하나다(`simulation/pixel-v2-2026-10-06-v01/pixel-simulation.js`). 시뮬레이션은 시작 전에 "칸들의 승·무·패 합계가 승·무·패 확률과 1e-6 이내로 같아야 한다"를 검사하고, 통과해야 칸 확률로 점수를 뽑는다. 서버 보고서(`report.cjs`)는 승·무·패 확률만 쓴다.
- 원본 JSON은 Python `json.dumps(..., separators=(',',':'), ensure_ascii=False)`로 바이트까지 재현된다. 원본은 보관된 v50 화면(`archive/visualizations/visualization-design-2026-10-08-v50/index.html`)에 그대로 남아 있다.

## 형식 후보와 측정값
| 방식 | 원본 크기 | 전송(gzip-6) | 시뮬레이션 검사(1e-6) | 값 변화 |
|---|---:|---:|---|---|
| 지금 (객체 169개) | 6.79MB | 1.47MB | 통과 | 없음 |
| A. 숫자 169개 배열, 원래 값 그대로 | 3.05MB | 1.17MB | 통과 (오차 9e-16) | 없음 |
| **B. 숫자 169개 배열, 유효숫자 8자리** | **2.13MB** | **0.70MB** | **통과 (최대 오차 1.2e-8)** | 칸마다 상대 오차 5e-8 이하 |
| C. 숫자 169개 배열, 소수 6자리 | 1.27MB | 0.24MB | **실패 (최대 오차 6.5e-6)** | 아주 작은 칸이 0이 됨 |

- 0.26.0 PR에서 "1.45MB → 0.24MB"라고 적은 것은 C 기준이었다. C는 시뮬레이션 검사를 통과하지 못하므로 그대로는 쓸 수 없다. 쓰려면 칸 값을 다시 맞추는(재정규화) 작업이 필요하고, 그러면 모델 출력값을 바꾸는 일이 되어 분석·예측 담당과 모델 평가가 필요하다.
- **채택안: B (유효숫자 8자리).** 전송량을 절반 이하로 줄이고, 모델 값은 사실상 그대로이며, 시뮬레이션 검사를 여유 있게 통과한다.

## 설계 (B안)
1. **파일 형식**: 각 예측에서 `scoreDistribution`을 지우고 `scoreGrid`(숫자 169개 배열, 홈 득점 우선 순서)를 넣는다. 값은 `float(f"{p:.8g}")`. 나머지 필드와 순서, 그리고 파일 맨 앞뒤의 `window.MatchLabData...=`·`;` 형식은 그대로 둔다. 파일은 Python 생성 스크립트(`design/release-0.26.1/compact_predictions.py`)로 v50 보관 원본에서 만든다. 손으로 고치지 않는다.
2. **화면에서 풀기**: 화면이 예측 파일을 읽는 한 곳에서, 경기마다 `scoreGrid`를 원래의 `{home, away, probability}` 객체 169개로 되돌려 `scoreDistribution`에 넣는다. 시뮬레이션 모듈과 나머지 화면 코드는 그대로다(공유 모듈의 바이트 동일 검사 유지).
3. **서버**: `report.cjs`는 승·무·패 확률만 읽으므로 바꾸지 않는다. 서버 검사의 "예측 값 = v50 원본" 비교는 "점수 분포를 뺀 모든 값 = 원본, 점수 칸 = 원본의 8자리 반올림"으로 바꾼다.
4. **공개 파일 검사(`check_release.py`)**: 복원 단계에서 예측 블록 자리에 v50 원본을 넣어 기존 v50 바이트 비교를 그대로 유지한다. 대신 예측 파일 자체에 대해 다음을 새로 확인한다:
   - 생성 스크립트를 다시 돌린 결과가 커밋된 파일과 바이트까지 같다.
   - 점수 분포 말고 모든 필드가 v50 원본과 같다.
   - 모든 칸이 원본의 8자리 반올림이고, 모든 경기의 승·무·패 합계 오차가 1e-6 미만이다.
   - `?v=` 해시가 새 파일과 맞는다.
5. **버전 기록**: VERSION·package.json 0.26.1, CHANGELOG, 이 명세의 실행 결과, manifest 갱신.

## 기대 효과와 한계
- 예측 파일: 6.79MB → 약 2.13MB, 전송 약 1.47MB → 약 0.70MB. 한국어 첫 방문 전송량은 약 1.7MB → 약 1.0MB가 될 것으로 예상한다(운영 측정으로 확인).
- 시뮬레이션은 같은 난수(시드)라도 아주 드물게 다른 점수를 뽑을 수 있다. 칸 값이 5e-8 이하로 달라져 경계에 걸리는 경우다. 검증에서 641경기 × 여러 시드로 실제 차이가 있는지 센다.
- 운영 서버(Vercel)의 brotli 전송은 gzip보다 오히려 크게 나온다(지금 예측 파일 1.63MB). 이번 범위에서는 바꾸지 않고 기록만 한다.

## 검증 계획
- 생성 스크립트 재실행 = 커밋된 파일(바이트 동일).
- 641경기 전부에서 점수 분포를 뺀 값 동일, 칸 오차, 승·무·패 합계 오차 1e-6 미만.
- 화면에서 되돌린 `scoreDistribution`이 원본과 칸마다 상대 오차 5e-8 이하이고, 시뮬레이션 검사를 통과한다.
- 시뮬레이션 비교: main(0.26.0)과 새 버전을 641경기 × 시드 20개로 돌려 결과(승무패·점수)가 다른 경우의 수를 센다. 0이 아니면 보고한다.
- 기존 검사: `npm run test:server`, `node server/check-vercel.cjs`, `node analysis/check.cjs`, `npm run test:report`, `npm run test:odds`, `python3 -I tools/check_release.py`.
- 브라우저: 한영 × 390/1440px, main과 화면 글자 비교(경기 목록·프리뷰·보고서·자연어 분석·시뮬레이션 확률), 페이지 오류 0, 가로 넘침 없음.
- 병합 후 운영 사이트에서 파일 해시, 실제 전송 크기, 화면 확인.
